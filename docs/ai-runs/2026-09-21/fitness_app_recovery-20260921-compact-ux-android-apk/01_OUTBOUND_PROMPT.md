# הפרומפט המחייב של הריצה (Claude Code · 2026-09-21) — נשמר במלואו

> נשלח על ידי אריאל דרך Claude Code. זהו מקור הסמכות של הריצה; הפידבק המחייב מופיע גם ב-`04_ARIEL_FEEDBACK.md`.

אתה ממשיך בפרויקט Fit Log לאחר השלמת, מיזוג ופרסום אזור חצאי המרתון.

## מטרת הריצה

בצע ריצה אוטונומית מלאה שמחברת שני יעדים:

1. שדרוג UX/UI רוחבי של האפליקציה, בדגש על היסטוריה, דיווח נתונים, ניווט, קומפקטיות ונראות.
2. מעבר מחוויית Web בלבד לאפליקציית Android מותקנת באמצעות APK תקין, משתחזר וניתן להורדה ולהתקנה.

התוצאה הרצויה היא אפליקציית כושר נעימה, קומפקטית ואינטואיטיבית, שמותאמת קודם כול לשימוש יומיומי בטלפון Android. גרסת ה־Web יכולה להמשיך להתקיים כתשתית וכערוץ משני; אין להשבית אותה או להסיר את Lovable ללא צורך מוכח.

אל תסתפק במחקר, מסמך המלצות, Mockup או build שלא נבדק. השלם מחקר, החלטה ארכיטקטונית, מימוש, בדיקות, PR, מיזוג, פרסום Web, בניית APK והפקת קובץ התקנה להורדה — אלא אם קיים חסם אמיתי ומתועד.

## פידבק המשתמש המחייב

הגישה להיסטוריה ואיסוף הנתונים עדיין אינה מספיק אינטואיטיבית וקלה.

כלל האפליקציה צריכה להיות:

* נעימה יותר לעין.
* קומפקטית יותר.
* בעלת טקסט שאינו גדול מדי.
* קלה להבנה ללא ניסוי וטעייה.
* מהירה לדיווח יומיומי.
* ברורה במעבר מסיכום לפרטים.
* עקבית בין ריצה, חדר כושר, פק״ל בבית, פרויקט חצי־המרתון והיסטוריה.
* מותאמת לשימוש כאפליקציית Android אמיתית, ולא כאתר מוקטן בתוך מסגרת.

ברירת המחדל בכל מסך צריכה להיות Snapshot קצר וברור. מידע נוסף ייפתח בלחיצה, במסך פירוט או באמצעות Progressive Disclosure.

Suunto יכולה לשמש רפרנס משמעותי, אך אין להעתיק אותה. שלב Best Practices ממספר אפליקציות מצליחות כדי לבנות מוצר המותאם לצרכים של אריאל.

אין לפתור את דרישת הקומפקטיות באמצעות הקטנה גורפת של כל הפונטים. נדרשים היררכיה נכונה, צפיפות מבוקרת, יעדי לחיצה נוחים ונגישות תקינה.

## פתיחת הריצה

לפני שינוי קוד:

1. קרא את `AGENTS.md`, הוראות המאגר, מסמכי `docs/ai`, הדוח האחרון וקפסולת הריצה האחרונה.
2. קרא את מקורות מערכת ההפעלה המחייבים בהתאם להוראות הפרויקט.
3. אמת את מצב `main`, ה־commit הנוכחי, האתר החי והקשר ביניהם.
4. אמת את מבנה הפרויקט וה־build הקיים לפני בחירת פתרון Android.
5. שמור את הפידבק הנוכחי במלואו בקפסולת הריצה.
6. פתח ענף ייעודי, למשל: `feat/compact-mobile-ux-android-apk`
7. אל תדרוס עבודה קיימת.
8. אל תשנה Auth, RLS, Supabase, הרשאות או מודל נתונים ללא צורך מוכח.
9. אין להפעיל Docker.

## חלק ז׳ — מעבר ל־Android APK

המוצר צריך להפוך לאפליקציית Android ניתנת להתקנה.

### החלטה ארכיטקטונית
בדוק את מבנה הקוד וה־build לפני בחירת הטכנולוגיה. השווה בקצרה בין האפשרויות הרלוונטיות, כגון: Capacitor עם WebView מקומי · Trusted Web Activity · PWA ארוז · פתרון Android אחר המתאים בפועל למאגר.

ברירת המחדל המועדפת היא פתרון שממחזר את קוד ה־Web הקיים, שומר על Source of Truth אחד ומאפשר build משתחזר. אל תבצע שכתוב ל־React Native או Native Android ללא צורך מוכח.

בחר פתרון לפי: עבודה ללא תלות בטעינת אתר חיצוני בכל פתיחה · תאימות ל־localStorage ולמנגנון הנתונים הקיים · התנהגות Android Back · קלט ומקלדת · RTL · Safe Areas · ביצועים · תחזוקה · build אוטומטי · אבטחה · יכולת עדכון גרסאות · אפשרות עתידית ל־Google Play, בלי להפוך פרסום בחנות לדרישת הריצה.

תעד את ההחלטה והחלופות שנדחו.

### דרישות APK
יישם: פרויקט Android תקין בתוך המאגר · Package/Application ID יציב ולא גנרי · שם אפליקציה `Fit Log` · אייקון ו־Splash Screen מתאימים מתוך נכסי המוצר הקיימים; אם אין נכס מתאים, צור גרסה נקייה ומינימלית · Version Name ו־Version Code מתועדים · RTL מלא · Status Bar ו־Navigation Bar מותאמים · Android Back תקין · פתיחת מקלדת ללא הסתרת שדות או כפתור השמירה · שמירת נתונים לאחר סגירה ופתיחה · מניעת איפוס נתונים בשדרוג גרסה · ללא הרשאות Android מיותרות · ללא סודות בתוך ה־APK · ללא מצב שבו build שקט מתחבר ליעד שגוי · מסך Offline/Error אמין אם התשתית דורשת רשת · קישורים חיצוניים נפתחים באופן בטוח · קישורים פנימיים נשארים בתוך האפליקציה · גיבוי ושחזור עובדים מתוך ה־APK.

אל תוסיף הרשאות מיקום, בריאות, אחסון רחב, מצלמה או התראות אם אין שימוש ממשי ומאושר.

### Build משתחזר
הכן תהליך build שאינו תלוי במחשב יחיד או בקובץ `.env` לא מתועד. דרישות: פקודת build מקומית מתועדת · workflow של GitHub Actions לבניית APK · lockfiles מחייבים · גרסאות Java/Android/Gradle/Node/Bun מקובעות כנדרש · build שנכשל אם Configuration מחייב חסר · ללא הדפסת secrets · artifact בשם ברור עם מספר גרסה · checksum מסוג SHA-256 · תיעוד מקור ה־commit שממנו נבנה · שמירת APK כ־GitHub Actions Artifact או GitHub Release, בהתאם למדיניות המאגר · אם ניתן, צרף את ה־APK גם כמסירה נגישה לאריאל.

אל תמציא signing credentials ואל תכניס keystore למאגר. אם אין keystore קיים ומורשה: בנה Debug APK או Release APK חתום בדרך בטוחה ומתועדת שמתאימה להפצה פנימית · ציין במפורש את סוג החתימה · אל תציג APK כמתאים ל־Play Store אם אינו עומד בדרישות · אל תעצור את כל העבודה בגלל שאין חתימת Store. אם קיים מנגנון חתימה מאושר במאגר או ב־GitHub Secrets, השתמש בו בלי לחשוף ערכים.

### שימור נתונים במעבר
האפליקציה הקיימת משתמשת בנתונים מקומיים. לכן חובה להכריע ולבדוק כיצד המעבר מהדפדפן ל־APK משפיע עליהם. אין להניח שה־APK יקבל אוטומטית את ה־localStorage של האתר.

בצע: 1. מיפוי מלא של כל מפתחות הנתונים הקיימים. 2. בדיקת מנגנון Export/Restore. 3. מסלול מעבר בטוח מה־Web ל־APK. 4. הוראות קצרות לאריאל: ייצוא גיבוי מה־Web · התקנת APK · שחזור באפליקציה · אימות מספר רשומות ונתוני מפתח. 5. בדיקת round-trip אמיתית. 6. הגנה מפני יבוא קובץ שגוי או חלקי. 7. מניעת דריסה שקטה של נתונים קיימים. 8. תיעוד rollback.

אם ניתן לבצע מעבר אוטומטי בטוח ללא הרשאות חריגות, אפשר ליישם אותו. אחרת, העדף Export/Restore מפורש ואמין.
